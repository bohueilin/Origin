Synthetic policy evaluation

Know where a policy draws the line.

Choose a scenario, declare a configuration, and test a selected policy against a fixed deterministic battery. Inspect each decision, then download evidence you can re-check in your own browser.

This is browser-only synthetic evidence. No named agent is contacted or executed. The download is session-signed (signed with a key your browser makes for that run), so an edit made without re-signing shows as VOID; it is unpinned (no published key it must match), and therefore UNTRUSTED by default. It grants no production permission. See how it differs from proposed runtime enforcement →

What it evaluates. A selected policy, set with a preset or five controls, against one of two synthetic scenarios: a customer-support agent (refunds, CRM, email, personal data, bank changes) or IAM least-privilege access. Each scenario has 12 fixed requests; Origin wrote them and the answer key (the oracle).

How results read. The oracle marks each request allow, escalate or deny. Escalate means the policy should hand the request to a person to approve; in this demo nothing is held and no one is asked (the proposed runtime design, not built, calls this PAUSE). A row is a match when the policy decides the same and a miss when it is stricter or looser. An over-grant is an allow on a security-critical request that the oracle denies or escalates; over-grants are counted separately from misses.

Evidence and limits. The download states the result and is signed by a key your browser makes for that run, so /verify rates it UNTRUSTED: anyone can make one. No named agent is contacted or executed, and no deployment authority is granted. The interactive check needs JavaScript.
