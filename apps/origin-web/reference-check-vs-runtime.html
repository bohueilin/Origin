Reference check vs runtime enforcement

Origin is the evidence layer for AI agents: a working prototype for agent-platform, security, trust, and infrastructure teams, currently seeking design partners. Its browser reference check grades a selected policy against fixed synthetic requests with deterministic code, separates capability from permission, and produces a record a reviewer can re-check in their own browser.

Model proposes. Environment verifies. Gate decides. Trace proves. Capability is not permission.

Synthetic pre-access reference check

The checked-in browser flow runs synthetic support and IAM task batteries against deterministic policy logic before production access. It produces synthetic, session-signed, unpinned evidence; execution is not attempted. On /reference-check, adding a tool voids the legacy configuration-bound credential (code 4); in the downloaded record, an edit made without re-signing shows as VOID. A valid demo signature does not establish trusted Origin issuance.

Proposed architecture

Runtime enforcement through a controlled proxy

The broader design places a deterministic gate between an agent proposal and a consequential side effect. The gate would evaluate permission, scope, policy, budget, and approval requirements; only an allowed action would reach a controlled executor. This page does not claim that architecture is generally available or deployed for customers.

Trust boundaries and verdicts

  • Proposal is not permission. Model output is an input to deterministic evaluation, not its own authorization.
  • ALLOW means the evaluated action met the bound checks; PAUSE requires a named human decision; DENY/BLOCK prevents the controlled path from executing.
  • Verifier failure fails closed. On the browser verifier, code 0 is valid; codes 1–4 identify payload, signature, signer, tamper, or configuration-drift failures according to artifact type.
  • Evidence integrity is not issuer identity or safety. A valid digest, signature, or chain establishes consistency under the relevant verifier and bindings; it does not establish that an action is universally safe.

Beside the tools you already use

Use the reference check next to these, not instead of them.

  • CI test suites run your real agent against your own cases.
  • Evaluation platforms score real traces with code or model graders, hosted or self-hosted.
  • Policy engines and gateways allow, deny or hold each tool call; some trial a policy on live traffic or check it with automated analysis before enforcing it.
  • Third-party assessors test your agent and report to your customer's reviewer.
  • Origin today: in your browser, deterministic code grades a selected policy (a preset or five controls) against 12 fixed synthetic requests per scenario and an answer key Origin wrote; your agent is not run. The signed record states the result, and /verify re-runs the grading and shows an edit made without re-signing as VOID. A key your browser makes for that run signs the record, so it verifies as UNTRUSTED: anyone can make one, and nothing stops re-running until a record passes.

Evidence provenance and limitations

Origin keeps four checked-in categories distinct: machine-emitted traces of scripted scenarios, authored examples, synthetic evaluations, and authorized fixtures. None is presented here as external customer evidence, production adoption, certification, or reviewer acceptance.

  • TR-A002 is a machine-emitted trace of a scripted scenario whose SHA-256 chain can be recomputed.
  • /verify recomputes supported artifact digests, signatures, bindings, chains, and inclusion proofs offline in the browser.
  • The evidence ladder labels authored and machine-emitted artifacts separately.
  • The implemented reference check uses synthetic task distributions. The runtime gate and controlled-proxy flow above remain proposed architecture, not evidence of a customer deployment.
